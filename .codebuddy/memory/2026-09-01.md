# 2026-09-01 工作记录

## ⚡ runTDXchuquan.py 增量化改造（方案 B）✅
- **痛点**：每次全量重算全市场（2949 万行日线 / 12140 只股票）+ 重写 fwd/bwd 两表 + 每股一个 commit（journal_mode=delete），极慢。
- **方案 B 落地**（cqInfo 快照 + SQL UPDATE 因子传播 + WAL）：
  - 新表 `cqInfo`（vnpy_adj_database.DbCqInfo）：每股一行存事件列表 JSON（**含算好的单事件因子 f**）+ 水位（last_bar_dt, bar_count）。
  - 新模块 `adjust_incremental.py`：`sync_adjusted()` 每股决策——无水位/事件被改/日线回填→全量重建（先删后插）；追加新事件→SQL UPDATE 因子传播；追加新日线→只算新 bar 插入；无变化→跳过。
  - `runTDXchuquan.py` 默认走增量；`--rebuild` 全量兜底；`-v` 每股动作；复权表被删/新建时自动强制全量。
- **关键数学事实（自定义口径下）**：新事件(date=D, 因子f)时，fwd(锚定首日,h) 只有 `bd>=D` 的行变（×f_old/f_new），bwd(锚定最新,q) 所有 `bd<D` 的行变（×f_new/f_old）→ 两表均可单条 UPDATE 传播，无需全量重算。
- **重要边界（调试发现）**：事件日 D ∈ (水位线, 新最大日线日] 时，新日线可能落在事件日之前 → `p_before`（除权前一日收盘）从旧水位线收盘变为事件日前最后一根新收盘 → **f 必须重算并传播 f_old→f_new**，否则增量与全量结果不一致（B 股测试用例抓出）。
- **写库优化**：`PRAGMA journal_mode=WAL`（持久，真实库已从 delete 切换）+ `synchronous=NORMAL`（每连接）+ 每股一个小事务（cqInfo 水位与数据同事务，中断可续）。
- **重构**：`adjust_factor_builder.build_adjusted_bars` 拆为 `_single_event_factor` / `compute_event_factors` / `adjusted_bars_from_factors`（数学逐字保留，增量模块复用同一口径）。
- **修过时测试**：`selftest_adj.py` 断言仍是 7-16 修复前的反向口径（fwd=[5,5,5]），已改为当前口径 fwd=[10,10,10](锚定首日)/bwd=[5,5,5](锚定最新)。
- **自测**：新增 `selftest_incremental.py`（临时库）：增量结果 vs 全量重建逐行一致(1e-9)、跳过轮零写入、回填触发全量、事件传播/未来事件跨越正确。两个自测均 PASS，lint 0。
